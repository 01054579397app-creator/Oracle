# Oracle Incident Log - errors

- [2026-10-01] TCP RST 및 Oracle TNS 통신 종료 분석
  - 질문 맥락: 사용자가 제공한 세 지점의 병합 pcapng에서 TCP reset 원인 후보를 확인했다. 원본은 변경하지 않았다. 외부 업무 정보 보호를 위해 내부 IP, 서버명, 업무 경로, 원문 패킷 및 Notion 링크는 기록하지 않는다.
  - 에러 메시지: Notion 본문은 로그인 필요로 미확인이다. 실제 ORA/TNS 오류 코드와 DB 설정은 확인하지 않았다. 패킷의 서버 응답은 TNS Data로 디코딩됐다. 이것만으로 Data Guard 구성 또는 업무 실패를 확정하지 않는다.
  - 확인된 패킷: 송신 측 A 캡처에서 한 TCP 세션의 RST 2개, 수신 측 캡처에서 동일 RST 2개가 확인됐다. 송신 측 B의 제공 캡처에서는 RST 0개다. 동일 패킷의 여러 지점 관측을 서로 다른 장애로 합산하지 않는다.
  - 종료 순서: 송신 측 A 캡처의 한국시간 기준 마지막 84바이트 데이터는 05:31:25.696086, 수신 측 ACK는 05:31:25.741966이었다. 05:31:56.015430에 송신 측 A가 10바이트 데이터를 보낸 뒤 05:31:56.015485에 FIN을 보냈고, 수신 측은 FIN까지 ACK했다. 05:32:02.207228에 수신 측의 320바이트 데이터가 도착하자 05:32:02.207264에 RST가 발생했고, 05:32:02.207314에 도착한 수신 측 FIN에도 05:32:02.207323에 두 번째 RST가 발생했다.
  - 해석: RST는 선행 FIN 이후의 후속 이벤트다. 송신 측 연결 종료 후 도착한 데이터/FIN에 대한 TCP 응답 패턴과 부합한다. 네트워크 장비가 최초 RST로 연결을 끊었다는 근거는 제공 캡처에서 찾지 못했지만 네트워크 문제 전체를 배제한 것은 아니다. 소켓을 닫은 정확한 응용 프로그램 이유는 미확인이다.
  - 원인 가설: 약 30초의 종료 전 대기와 약 5분의 후속 재접속은 응용 프로그램 타임아웃/재시도 설정과 대조할 가치가 있다. Oracle Data Guard 환경이라면 NET_TIMEOUT/REOPEN 및 전송 모드를 확인하되 실제 값으로 확인되기 전에는 원인으로 확정하지 않는다. TCP ACK와 Oracle 응용 계층 처리 응답을 구분한다.
  - 별도 관측: 문제 세션의 05:21:00~05:32:02 구간에서 수신 측 zero-window 패킷 34개, 33개 연속 관측 구간이 있었다. 모두 다시 열렸고 첫 zero-window부터 다음 nonzero-window까지의 가장 긴 관측 간격은 30.590ms였다. 캡처 관측 간격이며 정확한 내부 버퍼 체류 시간을 의미하지 않는다. 최종 연결 종료 직전 ACK의 raw window는 0이 아니었다.
  - 권장 조치: 양측 Oracle alert 및 transport/RFS 관련 trace를 05:31:20~05:32:10, 재접속 시각 05:37경과 대조한다. Data Guard 구성이라면 송신 측 전송 목적지의 NET_TIMEOUT, REOPEN, SYNC/ASYNC, AFFIRM 설정을 읽기 전용으로 확인한다. 수신 측 CPU/IO/redo 저장 지연은 가설이며 운영 증거로 검증한다. 원인 확인 전 타임아웃·버퍼 설정을 변경하지 않는다.
  - 검증 및 한계: 2026-10-01 Windows 로컬, Wireshark/TShark 4.6.9, 사용자 제공 실제 캡처의 오프라인 분석이다(Stub/AI 생성 데이터 아님). 세 병합 캡처의 RST 전수 검색과 양측 문제 세션의 FIN/ACK/SEQ 대조를 수행했다. 캡처 snaplen은 256바이트이며 시점 사이 누락 구간이 있다. SYN이 없는 구간의 window scale은 알 수 없다. 호스트 간 시계 차이가 있어 서로 다른 캡처의 절대 시각 차이를 편도 지연으로 해석하지 않는다.
  - 이전/이후 및 최적화: RST 의심을 선행 FIN 및 후속 RST 순서로 구체화했다. 원본 및 서비스 설정 변경은 없다. 문제 세션 중심으로 추가 확인 범위를 줄이는 구조적 효과만 있으며 속도·비용 개선 수치는 미실측이다.

## 추가 업데이트 — PDF 및 사용자 제공 RFS disconnect 기록 대조

- [2026-10-01] FIN 종료와 RST 후속 응답 및 캡처 누락 구간 구분
  - 추가 근거: 제공된 Notion PDF 10페이지의 본문과 1~3페이지 삽입 스크린샷을 확인했다. 사용자가 제공한 9개 시각은 RFS possible disconnect 8개와 ORA-16284 1개로 구분한다. 운영 서버나 DB에 접속해 원본 로그를 검증한 것은 아니다.
  - 21:05 사건: 수신 측 캡처에서 송신 측 B 주소의 FIN+10바이트 데이터가 2026-09-30 21:04:58.875060, 수신 측 FIN이 21:04:59.251014, 상대 ACK가 21:04:59.254923에 있었다. 사용자 제공 RFS 로그는 21:04:59.251180이다. 송신 측 A 주소의 FIN+10바이트 데이터는 21:04:59.550180, 수신 측 FIN은 21:05:00.772459, 상대 ACK는 21:05:00.776532이고 RFS 로그는 21:05:00.772613이다. RST 없이 TCP FIN/ACK 종료가 관측됐으며, 이는 응용 작업 성공을 의미하지 않는다. 이 시각 송신 호스트 원본 캡처는 제공되지 않아 주소 위조를 절대적으로 배제한 것은 아니다. RFS PID와 소켓의 직접 매핑은 미확인이다.
  - 05:32 사건 보강: 수신 측 동일 호스트 기록 시각 기준으로 데이터 송신 05:32:02.221389, FIN 송신 05:32:02.221471, 사용자 제공 RFS disconnect 로그 05:32:02.221697, 첫 RST 수신 05:32:02.225403 순이다. 로그가 RST 수신보다 기록 시각상 3.706ms 먼저다. 송신 측 선행 FIN은 수신 측 캡처에서 05:31:56.033615에 이미 관측됐다. RST가 이 disconnect의 최초 트리거라는 해석은 맞지 않는다. 미세한 시간차만으로 내부 코드의 인과관계를 확정하지는 않는다.
  - 캡처 포함 여부: 09-30 21:05의 두 사건은 수신 측 캡처만 포함, 10-01 05:32와 05:38:33은 세 캡처가 포함한다. 10-01 00:25:16, 02:28:02~03, 06:44:22의 사건 시각은 제공된 세 지점 캡처에 모두 없다. 해당 구간 직전 수신 측 파일 끝은 각각 00:23:58.080528, 02:25:17.655152, 06:41:30.663053이다. 병합 파일의 전체 시작~종료 범위를 연속 캡처로 취급하지 않는다.
  - 05:38:33 분류: ORA-16284는 진행 중인 작업의 완료를 기다리다 시간 초과됐다는 뜻이다. 해당 기록은 possible network disconnect 문구와 다른 종류이며, 그 시각의 RFS는 05:32 사건과 PID도 다르다. 재검토한 수신 측 분할 캡처에는 05:38:33 부근 FIN/RST가 없었다. 해당 작업 및 TCP 세션의 매핑과 trace 없이 RST 장애로 분류하지 않는다.
  - 이전 가설 정정: 사용자 RFS 기록은 ASYNC ORL이다. NET_TIMEOUT은 공식 문서상 SYNC redo 수신 확인 대기의 제어이므로, 앞선 30초 관측만으로 ASYNC 사건을 NET_TIMEOUT 원인으로 우선 귀속하면 안 된다. 실제 Oracle Net SEND/RECV timeout 설정과 전송 프로세스 trace를 먼저 대조한다. 약 5분 재접속은 REOPEN과 비교할 단서지만 설정값은 여전히 미확인이다.
  - PDF 해석 보완: PDF의 방화벽 허용 스크린샷은 09-28이며 Client RST Action 사례도 09-27~29의 별도 세션이다. 현재 09-30~10-01 사건의 직접 증거로 대체할 수 없다. FortiGate client-rst는 클라이언트 측 reset으로 세션이 종료됐다는 분류이며, 방화벽이 RST를 생성했다는 뜻이 아니다. 허용 로그는 순간 손실·지연 부재를 증명하지 않는다. 일부 보안장비의 RST injection은 가능한 가설이나 현재 관측으로 입증되지 않았다.
  - 수정 결론: 다른 disconnect에서 RST가 보이지 않는다고 다른 장비의 RST 또는 복합 RST를 결론낼 수 없다. 실제 FIN/ACK 종료 사례, 선행 FIN 이후 RST가 뒤따른 사례, 캡처가 없는 사건, 진행 중 작업 timeout을 구분해야 한다. 공통 원인이 여러 종료 형태를 낳을 가능성도 있어 종료 형태 차이를 원인 다양성의 증거로 삼지 않는다.
  - 다음 검증: 누락된 실제 장애 시각의 전후 분할 원본과 양 송신 노드 및 수신 노드의 연속 전체 TCP 캡처를 확보한다. 파일 이름이 아니라 최초/최종 패킷 시각으로 선정하고 장애 직전 구간, 장애 직후, 약 5분 재접속까지 포함한다. 이벤트에 대응하는 송신 transport 및 수신 RFS trace, 실제 적용된 Oracle Net timeout 설정, 목적지 REOPEN 설정을 읽기 전용으로 확인한다. 보안장비 개입은 같은 세션의 송수신 방향·SEQ/ACK·TTL 및 장비 raw log/정책과 대조한다. 원인 확인 전 운영 포트나 타임아웃을 변경하지 않는다.
