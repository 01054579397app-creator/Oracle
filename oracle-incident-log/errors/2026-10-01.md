# Oracle Incident Log - errors

- [2026-10-01] TCP RST 및 Oracle TNS 통신 종료 분석
  - 질문 맥락: 사용자가 제공한 세 지점의 병합 pcapng에서 TCP reset 원인 후보를 확인했다. 원본은 변경하지 않았다. 외부 업무 정보 보호를 위해 내부 IP, 서버명, 업무 경로, 원문 패킷 및 Notion 링크는 기록하지 않는다.
  - 에러 메시지: Notion 본문은 로그인 필요로 미확인이다. 실제 ORA/TNS 오류 코드와 DB 설정은 확인하지 않았다. 패킷의 서버 응답은 TNS Data로 디코딩됐다. 이것만으로 Data Guard 구성 또는 업무 실패를 확정하지 않는다.
  - 확인된 패킷: 송신 측 A 캡처에서 한 TCP 세션의 RST 2개, 수신 측 캡처에서 동일 RST 2개가 확인됐다. 송신 측 B의 제공 캡처에서는 RST 0개다. 동일 패킷의 여러 지점 관측을 서로 다른 장애로 합산하지 않는다.
  - 종료 순서: 송신 측 A 캡처의 한국시간 기준 마지막 84바이트 데이터는 05:31:25.696086, 수신 측 ACK는 05:31:25.741966이었다. 05:31:56.015430에 송신 측 A가 10바이트 데이터를 보낸 뒤 05:31:56.015485에 FIN을 보냈고, 수신 측은 FIN까지 ACK했다. 05:32:02.207228에 수신 측의 320바이트 데이터가 도착하자 05:32:02.207264에 RST가 발생했고, 05:32:02.207314에 도착한 수신 측 FIN에도 05:32:02.207323에 두 번째 RST가 발생했다.
  - 해석: RST는 선행 FIN 이후의 후속 이벤트다. 송신 측 연결 종료 후 도착한 데이터/FIN에 대한 TCP 응답 패턴과 부합한다. 네트워크 장비가 최초 RST로 연결을 끊었다는 근거는 제공 캡처에서 찾지 못했지만 네트워크 문제 전체를 배제한 것은 아니다. 소켓을 닫은 정확한 응용 프로그램 이유는 미확인이다.
  - 원인 가설: 약 30초의 종료 전 대기와 약 5분의 후속 재접속은 응용 프로그램 타임아웃/재시도 설정과 대조할 가치가 있다. Oracle Data Guard 환경이라면 NET_TIMEOUT/REOPEN 및 전송 모드를 확인하되 실제 값으로 확인되기 전에는 원인으로 확정하지 않는다. TCP ACK와 Oracle 응용 계층 처리 응답을 구분한다.
  - 별도 관측: 문제 세션의 05:21:00~05:32:02 구간에서 수신 측 zero-window 패킷 34개, 33개 연속 관측 구간이 있었다. 모두 다시 열렸고 첫 zero-window부터 다음 nonzero-window까지의 가장 긴 관측 간격은 30.590ms였다. 캡처 관측 간격이며 정확한 내부 버퍼 체류 시간을 의미하지 않는다. 최종 연결 종료 직전 ACK의 raw window는 0이 아니었다.
  - 권장 조치: 양측 Oracle alert 및 transport/RFS 관련 trace를 05:31:20~05:32:10, 재접속 시각 05:37경과 대조한다. Data Guard 구성이라면 송신 측 전송 목적지의 NET_TIMEOUT, REOPEN, SYNC/ASYNC, AFFIRM 설정을 읽기 전용으로 확인한다. 수신 측 CPU/IO/redo 저장 지연은 가설이며 운영 증거로 검증한다. 원인 확인 전 타임아웃·버퍼 설정을 변경하지 않는다.
  - 검증 및 한계: 2026-10-01 Windows 로컬, Wireshark/TShark 4.6.9, 사용자 제공 실제 캡처의 오프라인 분석이다(Stub/AI 생성 데이터 아님). 세 병합 캡처의 RST 전수 검색과 양측 문제 세션의 FIN/ACK/SEQ 대조를 수행했다. 캡처 snaplen은 256바이트이며 시점 사이 누락 구간이 있다. SYN이 없는 구간의 window scale은 알 수 없다. 호스트 간 시계 차이가 있어 서로 다른 캡처의 절대 시각 차이를 편도 지연으로 해석하지 않는다.
  - 이전/이후 및 최적화: RST 의심을 선행 FIN 및 후속 RST 순서로 구체화했다. 원본 및 서비스 설정 변경은 없다. 문제 세션 중심으로 추가 확인 범위를 줄이는 구조적 효과만 있으며 속도·비용 개선 수치는 미실측이다.
