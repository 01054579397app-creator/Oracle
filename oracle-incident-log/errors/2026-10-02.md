# Oracle Incident Log - errors

- [2026-10-02] 추가 업데이트 — 양측 alert 원본 대조 및 송신·수신 timeout 사건 구분
  - 질문 맥락: 제공된 송신 측 및 수신 측 alert 로그를 기준으로 Data Guard disconnect의 선행 오류부터 다시 조사했다. 내부 IP, 서버명, PID, 업무 경로, 원문 로그 및 대화 전체는 기록하지 않는다. 이전 분석은 errors/2026-10-01.md에 보존한다.
  - 검증 범위: Windows 로컬에서 실제 제공 파일 두 개를 바이트 단위로 끝까지 순차 분석했다. 송신 측은 424735줄이며 첫 timestamp는 2026-07-13 08:05:29, 마지막은 2026-10-02 16:03:41이다. 수신 측은 211549줄이며 첫 timestamp는 2025-12-24 15:15:21, 마지막은 2026-10-02 15:42:34다. 이 범위가 모든 시각의 상세 동작 기록을 보장하지는 않는다. 검색 도구의 부분 결과로 해당 날짜 기록이 없다고 판단할 수 없으며, 전체 순차 분석과 해당 줄의 직접 읽기로 보정했다. 한국어 메시지의 표시 인코딩 문제는 오류 번호와 ASCII 필드를 기준으로 구분했다.
  - 09-30 21:05 사건: 송신 측 alert의 21:04:24.147881 네트워크 오류는 main 12535, secondary 12608이며 해당 DR 서비스 주소·포트에 대응한다. 21:04:54.178245에도 같은 secondary 12608이 있다. 21:04:58.393580에 전송 프로세스가 목적지 2 재연결을 시도·포기했고 ORA-16038이 뒤따른다. 수신 측 Thread 1 / Sequence 611 disconnect의 client PID가 송신 프로세스와 일치한다. 앞서 측정된 zero-window 21:03:52.385329~21:04:57.372570 및 transport trace의 최초 12608과 부합한다. 기존 패킷은 재분석하지 않았다.
  - 10-01 05:32 사건의 새 근거: 송신 측 05:31:56.014409 오류의 secondary는 12609이며 해당 DR 서비스 주소·포트다. 05:31:56.039679에 별도 전송 프로세스의 Error 12609가 기록됐다. 수신 측 05:32:02.221697의 Thread 1 / Sequence 615 disconnect에 기록된 client PID가 이 송신 프로세스와 일치한다. 따라서 이 사건의 관측된 선행 실패는 송신 timeout 12608이 아니라 수신/read timeout 12609다. 이전 패킷의 Primary 선행 FIN과 후속 RST 순서에 대응하는 응용 계층 근거가 추가됐다. 어떤 Oracle 응답을 기다렸는지는 아직 미확인이다.
  - 오류 구분: 공식 문서상 12608은 send/write timeout, 12609는 receive/read timeout이다. Fatal NI connect error 12170 또는 main 12535만 보고 모두 동일한 장애로 묶지 않고 secondary code와 상대 주소·포트, Thread/Sequence 및 client PID를 대조한다. TCP ACK 수신을 Oracle 작업 완료로 해석하지 않는다.
  - 다른 사건: 10-01 02:27:41.534506과 06:43:44.815913의 송신 측 alert에서도 DR 서비스에 대한 secondary 12608을 확인했다. 대응 수신 측 Thread 1 / Sequence 615 및 618 disconnect는 같은 전송 프로세스의 client PID를 기록한다. 패킷 누락 때문에 두 사건의 zero-window 원인은 확정하지 않는다. 00:25의 수신 측 disconnect는 Thread 2이며 제공된 송신 측 Thread 1 로그만으로 해당 Primary 오류를 대조할 수 없다.
  - 공통 영향 단서: 09-30 21시, 10-01 02시 및 06시 사건에서 수신 측 Thread 1과 Thread 2 disconnect가 근접해 나타난다. DR 공통 자원 또는 공통 네트워크 경로를 우선 조사할 근거이나, DR 자원 문제나 보안장비 개입을 확정하지 않는다.
  - 수신 측 추가 단서: 문제 시퀀스의 redo 복구 기록에는 ASM과 파일시스템 멤버가 함께 나타난다. 실제 standby redo 구성과 쓰기 대상은 별도 읽기 전용 조회로 검증하고 두 저장 경로의 지연을 조사한다. 복구 기록만으로 모든 멤버의 쓰기 대기 또는 snapshot 작업 실행을 확정하지 않는다. RFS action IDLE, elapsed idle time 0 또한 사건 전 구간의 IO 지연 부재를 증명하지 않는다.
  - 권장 조치 및 검증 항목: 09-30 사건의 송신 transport trace와 대응 수신 RFS trace를 21:03:40~21:05:10에 대조한다. 05:32 사건은 별도 송신 transport trace와 대응 수신 RFS trace를 05:31:20~05:32:10에 대조하고, 이후 FAL 작업의 ORA-16284 trace는 후속 gap 처리의 별도 근거로 확인한다. 필요한 trace는 제공 폴더의 파일명 검색에서 찾지 못했으며 운영 서버 보존 여부는 미확인이다. 같은 시각의 DR CPU·IO·ASM·파일시스템·정기 작업 및 양측 실제 timeout 설정을 확인한다. 원인 확정 전 버퍼·timeout·숨은 파라미터·포트·보안 정책을 변경하지 않는다.
  - 이전/이후 및 최적화: 송신 timeout 중심의 기존 설명에서 사건별 송신 12608과 수신 12609를 분리하고, 원본 양측 로그의 Thread/Sequence 및 client PID 대응으로 근거를 보강했다. 실제 제공 로그의 오프라인 분석이며 Stub 데이터가 아니다. 원본 alert·PCAP와 운영 설정은 변경하지 않았다. 후속 trace 조사 범위를 사건별로 좁혔으며 속도·비용 효과는 미실측이다.
