- 주제: RMAN 제외 테이블스페이스 복구 후 OPEN RESETLOGS
- 질문 맥락: 원본에서 `CONFIGURE EXCLUDE FOR TABLESPACE TS_KR_META`로 해당 테이블스페이스를 제외해 데이터베이스를 백업하고, 대상에서 `RESTORE DATABASE SKIP TABLESPACE TS_KR_META`, `RECOVER DATABASE SKIP TABLESPACE TS_KR_META` 후 `ALTER DATABASE OPEN RESETLOGS`를 수행할 때의 문제점 확인.
- 오류 메시지: 일반 `SKIP TABLESPACE`는 대상 데이터파일을 OFFLINE으로 남기지만 `FOR DROP` 상태로 만들지 않으므로, `OPEN RESETLOGS` 시 `ORA-01245: offline file ... will be lost if RESETLOGS is done`이 발생할 수 있음.
- 원인 가설: 컨트롤파일에는 `TS_KR_META` 데이터파일 항목이 남아 있고, 백업에서는 파일을 제외했으며, 일반 `RECOVER ... SKIP TABLESPACE`는 파일을 OFFLINE 처리할 뿐 영구 폐기 표시를 하지 않음.
- 권장 조치: 테이블스페이스를 대상에서 영구 폐기할 목적이면 `RECOVER DATABASE SKIP FOREVER TABLESPACE TS_KR_META`를 사용해 데이터파일을 OFFLINE FOR DROP 상태로 만든 뒤 `ALTER DATABASE OPEN RESETLOGS`를 수행하고, 오픈 후 `DROP TABLESPACE TS_KR_META INCLUDING CONTENTS AND DATAFILES`로 정리. 보존할 목적이면 제외하지 말고 해당 데이터파일을 복원·복구하여 ONLINE으로 전환.
- 검증 항목: 오픈 전 `V$DATAFILE`과 `V$TABLESPACE`로 대상 파일 상태 확인, RMAN 복구 로그에서 `SKIP FOREVER` 및 OFFLINE DROP 처리 확인, 오픈 후 테이블스페이스 제거 여부와 비제외 데이터파일의 복구 완료 상태 확인. `TS_KR_META`에 UNDO 또는 필수/SYS 소유 객체가 없는지도 사전 검증.

## 추가 업데이트: 아카이브 복구와 RESETLOGS 필요 조건

- 범위 정정: 아카이브드 로그를 적용했다는 사실만으로 `RESETLOGS`가 필요한 것은 아님.
- `RESETLOGS` 없이 오픈 가능한 조건: 현재 컨트롤파일(`V$DATABASE.CONTROLFILE_TYPE='CURRENT'`)을 유지하고, `UNTIL`이나 로그 누락 없이 완전복구한 경우 `ALTER DATABASE OPEN`으로 오픈 가능. 이때 일반 `RECOVER DATABASE SKIP TABLESPACE TS_KR_META`로 제외 파일을 OFFLINE 상태로 유지한 뒤 오픈 후 해당 테이블스페이스를 삭제할 수 있음.
- `RESETLOGS`가 필수인 조건: 백업/오토백업 컨트롤파일을 복원해 사용한 경우에는 모든 아카이브드 로그와 온라인 리두를 적용해 완전복구했더라도 `OPEN RESETLOGS`가 필수. 또한 `SET UNTIL`, 로그 누락, `UNTIL AVAILABLE REDO` 등 불완전복구 후에도 필수.
- 운영 판단: `SELECT CONTROLFILE_TYPE FROM V$DATABASE`와 실제 컨트롤파일 복원 이력을 먼저 확인. `CURRENT`이고 완전복구가 끝났다면 `ALTER DATABASE OPEN`을 사용하며, `BACKUP`이면 지원되는 일반 복구 절차에서 `RESETLOGS`를 피할 수 없음.
