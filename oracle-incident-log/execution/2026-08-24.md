## 5. ACTIVE MOUNT 전환 중 발생한 타임아웃과 확인 과정

실제 실행:

```bash

SQL
EOSU
```

원격 실행기가 30초 내 출력을 반환하지 않았다. 같은 `startup mount`를 다시 실행하지 않고 다음 진단을 실행했다.

```bash
set echo on feedback on pages 100 lines 200
select instance_name, status, database_status from v$instance;

SQL
EOSU
```

출력:

```text
INSTANCE_NAME STATUS  DATABASE_STATUS
ACTIVE        STARTED ACTIVE

ORA-01507: database not mounted
```

이 값만 보면 MOUNT 실패처럼 보이지만, `startup mount` 원래 세션이 아직 실행 중이었다. alert 확인을 처음 다음처럼 잘못 입력했다.

판단:

## 13. PRIMARY를 FSYNC 우선 경로로 failback

SRL 복구 직후 PRIMARY는 아직 ACTIVE 직송을 사용하고 있었다.

```text
dest 2 ACTIVE VALID
dest 3 FSYNC  ALTERNATE
```

ACTIVE 직송은 그대로 ENABLE인 상태에서 FSYNC destination만 재접속하고 로그 스위치를 실행했다.

```bash
su - oracle <<'EOSU'
export ORACLE_SID=DMHOME1
sqlplus / as sysdba <<'SQL'
set echo on feedback on pages 1000 lines 300 trimspool on
col destination format a30
col error format a60
alter system set log_archive_dest_state_3='DEFER' scope=both sid='*';
alter system set log_archive_dest_state_3='ENABLE' scope=both sid='*';
alter system archive log current;
select inst_id, dest_id, status, destination, transmit_mode, affirm,
       db_unique_name, error
from gv$archive_dest
where dest_id in (2,3)
order by inst_id, dest_id;
exit
SQL
EOSU
```

## 16. 실제 원인과 복구 명령의 연결

1. `/arch` 전체 CATALOG가 과거 branch를 ACTIVE controlfile에 등록했다.
2. 08:40:26 recovery target이 incarnation 2로 바뀌었다.
3. 정상 MRP가 `ORA-19906`으로 중단되고 재기동 시 `ORA-19909`가 발생했다.
4. `RESET DATABASE TO INCARNATION 1`로 datafile/PRIMARY와 같은 branch를 다시 CURRENT로 만들었다.
5. ACTIVE는 MRP 재기동 후 lag 0으로 따라잡았다.
6. FSYNC는 별개로 controlfile에만 남은 SRL 멤버와 실제 ASM 파일이 불일치했다.
7. 누락 SRL 네 개를 `CLEAR UNARCHIVED LOGFILE`로 OMF 재생성했다.
8. PRIMARY dest 3을 재접속해 `PRIMARY → FSYNC → ACTIVE` 우선 경로로 failback했다.

## 17. 재발 방지

- 공용 `/arch` 루트에 `CATALOG START WITH '/arch'`를 실행하지 않는다.
- catalog가 필요하면 `DB_UNIQUE_NAME`, branch/resetlogs ID와 개별 파일을 먼저 확인한다.
- PRIMARY의 `DELETE ARCHIVELOG ALL`은 standby 필요 로그를 `RMAN-08137`로 보호하지만, ACTIVE/FSYNC에서 공용 경로를 catalog한 뒤 삭제하면 다른 DB의 파일까지 범위에 들어갈 수 있다.
- FSYNC/ACTIVE SRL은 controlfile 등록뿐 아니라 `V$LOGFILE.MEMBER`의 ASM 실파일 존재까지 확인한다.
- 현재 PRIMARY online redo는 thread별 2개이고 ACTIVE/FSYNC SRL도 thread별 2개다. 운영 안정성 관점에서 `online redo 그룹 수 + 1` SRL 확보는 별도 변경 작업으로 검토한다.
